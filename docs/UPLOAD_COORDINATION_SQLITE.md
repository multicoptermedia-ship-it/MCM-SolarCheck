# SQLite upload coordination prototype

`SQLiteUploadLeases(database, lease_seconds=60)` provides an opt-in, token-owned coordination table shared by cooperating processes accessing **the same SQLite database**. It implements `hold(customer_id, project_id, filename)` for the existing optional `file_locks` interface on the filesystem upload store and upload reconciliation. Busy leases raise `UploadLeaseBusy`; they are not silently ignored. Expired leases may be reclaimed; stale tokens cannot renew or release a successor's lease.

**Not production-ready:** `hold()` now starts a heartbeat thread that renews the lease periodically and raises `UploadLeaseLost` at normal context exit if ownership cannot be confirmed. However, a lease can still expire while a blocking filesystem/SFTP operation is underway, and that operation may already have written data before the loss is detected. It has no fencing token enforced by storage, no crash-safe atomic commit across SFTP and SQLite, and no protection against non-cooperating writers. The SQLite database must be on a suitable shared coordination host, not copied separately to each worker. Do not place SQLite directly on unreliable network/SFTP filesystems. Production requires a centralized transactional coordinator with fencing and heartbeat/renewal, plus IONOS SFTP integration tests and explicit deployment configuration. Nothing is automatically enabled, deployed, or billed by this prototype.

Heartbeat threads are stopped and joined when the context exits. The lease is still advisory, without fencing enforced by the remote storage system; therefore an expired owner is not guaranteed to stop writing. Production use requires a storage-level commit protocol, fencing/conditional writes, monitoring and worker coordination. No live HTTP wiring or deployment was enabled.
